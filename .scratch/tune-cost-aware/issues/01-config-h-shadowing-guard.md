# 01 — Guard against `include/config.h` shadowing CMake builds

Status: done

## The defect

Configuring the Autotools build writes a generated `include/config.h` into the
**source tree**. From then on, every CMake build in that tree compiles against
that file instead of its own `config.h`, and silently takes the Autotools
tree's precision. No error, no failed build — just a library with the wrong
name mangling and the wrong `R` type.

Observed: after `./configure && make` in a tree that also had CMake build
directories, `bx-f/kernel/libnfft3f.so` exported **`nfft_tune`** (double
mangling) and no `nfftf_tune` at all. The float test binary then failed to
link. Had it linked, it would have silently tested double precision.

## Root cause

`include/infft.h` line 25 does

```c
#include "config.h"
```

A **quoted** include searches the directory of the *including file* before any
`-I` path. `infft.h` lives in `include/`, so when `include/config.h` exists it
wins. Include-path order cannot fix this and is not worth adjusting:
`NFFT_GENERATED_INCLUDE_DIR` (`${PROJECT_BINARY_DIR}`, where CMake writes its
own `config.h`) comes first for some targets and after
`${PROJECT_SOURCE_DIR}/include` for others — for example
`cmake/nfft_interface_kernel.cmake:16-18` lists the source `include/` first —
and the quoted-include rule overrides both.

The two headers also differ in a way that makes the failure silent:

- CMake's (`cmake.config.h.in`) opens with `#ifndef NFFT_CONFIG_H`.
- Autotools' (autoheader-generated) has **no include guard**, and spells the
  precision selectors as `/* #undef NFFT_SINGLE */` — a comment. It does not
  unset anything; it simply never defines `NFFT_SINGLE` or `NFFT_LDOUBLE`, and
  `infft.h` falls through to its double-precision branch (`infft.h:68,79`).

Where both headers get read in one translation unit, the `HAVE_DECL_*` macros
are redefined and the compiler emits a wall of `warning: "HAVE_DECL_ACOS"
redefined` — the only visible symptom, and easy to dismiss as noise.

`include/config.h` is gitignored (`.gitignore:79`), so it never shows up in
`git status` either.

## Reproduce

```sh
cmake -S . -B bx-f -DNFFT_ENABLE_FLOAT=ON -DNFFT_ENABLE_TESTS=ON \
      -DCMAKE_BUILD_TYPE=Release
cmake --build bx-f -j --target nfft3
nm -D bx-f/kernel/libnfft3f.so | grep -c nfftf_malloc   # non-zero: correct

./bootstrap.sh && ./configure --enable-all && make -j    # writes include/config.h
cmake --build bx-f -j --clean-first --target nfft3
nm -D bx-f/kernel/libnfft3f.so | grep -c nfftf_malloc   # 0: wrong precision
```

Clean up with `rm -f include/config.h` (or `make distclean`).

## Fix

**Required — refuse to configure.** In `CMakeLists.txt`, next to the precision
block (currently around line 102), fail when the stale header is present:

```cmake
if(EXISTS "${PROJECT_SOURCE_DIR}/include/config.h")
  message(FATAL_ERROR
    "${PROJECT_SOURCE_DIR}/include/config.h exists. It is generated by the "
    "Autotools configure and, because include/infft.h includes \"config.h\" "
    "with quotes, it overrides this build's own config.h and silently changes "
    "its precision. Run 'make distclean' in the source tree (or delete the "
    "file) and re-run CMake. Set NFFT_ALLOW_INTREE_CONFIG_H=ON to override.")
endif()
```

Gate it on an escape hatch (`option(NFFT_ALLOW_INTREE_CONFIG_H ...)` defaulting
`OFF`) so nobody is stuck. Configure-time only is not quite enough, because the
file can appear *after* CMake configures — which is exactly what happened. So
also add:

**Required — catch it at build time.** A post-build check on the kernel target
that the library exports the mangled prefix the tree was configured for. The
suffix is already available as `NFFT_PREC_SUFFIX` (`CMakeLists.txt:103-112`).
Either a `add_custom_command(TARGET nfft3 POST_BUILD ...)` running `nm`, or —
more portable and cheaper — a compile-time assertion in a small source file
compiled into the kernel:

```c
/* precision_guard.c, compiled with the same flags as the kernel */
#include "infft.h"
#if defined(NFFT_SINGLE)
  #define NFFT_GUARD_SUFFIX_IS_F 1
#elif defined(NFFT_LDOUBLE)
  #define NFFT_GUARD_SUFFIX_IS_L 1
#endif
/* CMake passes -DNFFT_GUARD_EXPECT_{F,L,D}=1 from NFFT_PREC_SUFFIX; the file
   #errors when the two disagree. */
```

The compile-time form is preferred: it needs no `nm`, works on every platform,
and fires on the exact translation-unit path that the bug travels down.

**Optional, deeper.** Change `include/infft.h` to `#include <config.h>`, which
skips the includer-directory rule and obeys `-I` order. This removes the
mechanism rather than detecting it, but it must not break out-of-tree Autotools
builds: `kernel/*/Makefile.am` currently pass only `-I$(top_srcdir)/include`,
so `$(top_builddir)/include` would have to be added everywhere `config.h` is
reachable. Treat as a follow-up, not part of this issue.

## Not to be confused with

`cmake/config-parity-check.sh`, which diffs the *macro symbol set* between the
two build systems' headers. That guards against config drift. This issue is
about one header shadowing the other at compile time. Give the new guard a
distinct name in any message or comment so the two stay separable.

## Acceptance

- With `include/config.h` present, `cmake -S . -B <dir>` fails with a message
  naming the file and the fix.
- With `include/config.h` appearing after configure, the build fails rather
  than producing a wrong-precision library.
- `NFFT_ALLOW_INTREE_CONFIG_H=ON` restores the old behaviour.
- All three precision trees still configure, build and pass `checkall_ng` when
  no stale header is present.
- The full Autotools `--enable-all` build still works (run it last, then delete
  `include/config.h`).

## Resolution

Three layers, all named "in-tree config.h guard" to keep them apart from
`cmake/config-parity-check.sh`:

- `cmake/nfft_intree_config_h.cmake` refuses to configure while
  `include/config.h` exists. The same file runs as a `cmake -P` script from
  the `nfft3_intree_config_h_guard` target, which the kernel targets depend
  on, so it also fires when the file appears after configure.
- `kernel/util/config_guard.c` compares the precision CMake configured
  (`NFFT_CONFIG_GUARD_PRECISION`, set with `add_compile_definitions`) against
  the one the `config.h` actually read selects, and `#error`s on a mismatch.
  Autotools leaves the macro unset and compiles the file to nothing.
- `NFFT_ALLOW_INTREE_CONFIG_H=ON` turns all of it off.

Verified: configure refused with the file present; a build of an
already-configured float tree refused after the file appeared; the guard
translation unit `#error`ed when compiled by hand against a double
`config.h` in a float tree; the escape hatch configured cleanly; and all
three precision trees configure, build and pass `checkall_ng` without it.
