X(trafo_direct)() — phase recurrence in the 1d direct NDFT

Replace two transcendentals per inner-loop iteration with one complex multiply. A large, precision-dependent win — up to ~3.9× in long double — but with one reproducible float side-effect the matrix caught.

⚠ Landed with caveat — the target speeds up in every precision (~1.3× double, ~1.6× float, ~3.9× long double) with the 116-case correctness net green in all three. 1 · The target — what we optimized and why

X(trafo_direct) is the direct (O(N·M)) nonequispaced DFT; its 1d hot loop evaluates COS/SIN on every inner iteration. It is precision-agnostic, so it must be validated in float, double, and long double — where the per-call trig cost differs by orders of magnitude.

/* 1d branch, before */
for (k_L = 0; k_L < ths->N_total; k_L++) {
  R omega = K2PI * ((R)(k_L - ths->N_total/2)) * ths->x[j];
  v += f_hat[k_L] * (COS(omega) - II * SIN(omega));   /* 2 transcendentals / term */
}

2 · The idea — what to change, and the reasoning

omega_k advances by a constant Δ = 2π·x[j] as k grows, so the kernel e−iω is a geometric sequence: evaluate the two trig calls once per node, then carry the phase by one complex multiply per term (phase recurrence / strength reduction).

/* 1d branch, after */
C w  = COS(omega0) - II * SIN(omega0);   /* start phase */
C dw = COS(domega) - II * SIN(domega);   /* step factor */
for (k_L = 0; k_L < ths->N_total; k_L++) { v += f_hat[k_L] * w; w *= dw; }
Risk watched: rounding drift over N steps — checked against the net tolerance in every precision. It held (float included).

  • Known: adjoint_direct is not touched by this change, yet float adjoint_1d[32/100] is a stable ~8480 ns vs a stable reverted-baseline ~7840 ns (confirmed by reverting + rebuilding + 4+3 independent runs). Cause: enlarging the sibling trafo_direct shifts adjoint_direct's code placement → i-cache/alignment on the smallest case. It is precision-specific — in double the same case is noise.
  • Mechanism confirmed = alignment. Rebuilding the float tree with -falign-functions=64 -falign-loops=32 (everything else equal) returns adjoint_1d[32/100] to ~7840 ns (regression gone) while the target forward_1d[32/100] stays ~4470 ns (~1.7×). So it is alignment roulette, not an algorithmic change to adjoint — deterministic alignment makes the neighbour insensitive to trafo_direct's size.
  • To resolve (recommended): add -falign-functions=64 as a separate build-policy change — it removes this regression and damps the broader walltime layout jitter, without touching the optimization diff. Alternatives: accept + document (the regressed case is an 8 µs op on the slow reference path), or revert. 6 · Patterns

Used

  • Phase recurrence — a constant-step phase is a geometric sequence; carry by multiplication.
  • Strength reduction — per-iteration transcendentals → one complex multiply.

Discovered

  • The win is precision-dependent (1.3× / 1.6× / 3.9×) and largest where the baseline is worst (long double). Double-only would report only the floor.
  • Code layout can regress an untouched sibling — and only in one precision. The full per-precision exit gate is what surfaced it; a scoped or double-only check would not.

7 · Carry-forward notes

  • Clear stale in-source include/config.h before configuring precision trees (a leftover Autotools double config silently breaks float/long-double linking). CI does this; the skill now does too.
  • Long double trig is ~250× double on this hardware — any cos/sin-heavy kernel is a prime long-double optimization target, with outsized payoff there.
  • The same recurrence applies to adjoint_direct and the multivariate branches (untouched here) — obvious next targets, and doing adjoint too might offset the layout shift.
  • Re-run flagged walltime cases — 2 of 3 float flags here were noise that vanished on re-run; only the reverted-baseline comparison proved the third real.
